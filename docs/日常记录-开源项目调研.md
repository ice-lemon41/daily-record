**目标**：为「日常记录」产品寻找可参考的实现，产品形态未定，但主要在 Android 手机上使用。

**筛选标准**：

1. 能在 Android 上真实使用（原生 APK、跨平台 APK，或移动端 Web）；
2. 有真实用户量（Star / 下载量）且仍在维护；
3. 形态、技术栈或功能定位彼此不同，避免样本重复；

## 2. 结论速览

| 项目 | Star | 协议 | 技术栈 | 测试 | 同步 / 备份 | 最值得参考 |
|------|------|------|--------|------|-------------|------------|
| Memos | 64.5k | MIT | Go + SQLite/MySQL/PostgreSQL + React | Go 单测较完整 | 自托管，无端云同步 | 极简输入、时间线、标签、单二进制部署 |
| 侠客日记 | 1.6k | AGPL-3.0 | .NET 10 + Blazor Hybrid/Server/WASM + SqlSugar | 仓库内无自动化测试 | WebDAV 备份、局域网传输 | 一套 UI 多端复用、本地优先、隐私模式 |
| June | 337 | GPL-3.0 | Kotlin + Compose + Room + Koin | core 模块约 44 个测试文件 | 本地优先 + WebDAV / Google Drive | 数据模型、软删除与同步字段、导入迁移 |
| Easy Diary | 564 | GPL-3.0 | Kotlin + Room + MVVM + XML | 约 6 个测试文件 | Google Drive（仅 GMS 版） | 功能需求池、日历/时间线/图表三视图、双渠道打包 |
| Loop Habit | 10.4k | GPL-3.0 | Kotlin Multiplatform + SQLite | 56 个 common 测试 + 111 个 Android 测试 | CSV / SQLite 导出，无云 | 纯逻辑核心、迁移测试、极简离线体验 |

**五条关键结论**：

1. **「本地优先」几乎是共识**。五个项目里，四个默认数据在本地，云只作为可选备份/同步；唯一以服务端为中心的 Memos 也强调「数据在你自己的服务器上」。
2. **数据模型高度趋同**：`条目 + 标签 + 附件 + 时间戳`，再加软删除、同步状态字段。差异主要在多媒体和结构化字段（心情、天气、位置、音乐）。
3. **升级迁移是最大的数据风险**。Easy Diary 从 Realm 迁移到 Room 后出现「所有日记消失」的线上事故（[#256](https://github.com/hanjoongcho/aaf-easydiary/issues/256)），这是最值得警惕的案例。
4. **功能膨胀会反噬体验**。侠客日记被用户直接吐槽「打开要四五秒，只需要一个能写字的本地便签」（[#44](https://github.com/Yu-Core/SwashbucklerDiary/issues/44)），冷启动和闪退也是其 Issues 里的高频问题。
5. **同步不等于备份**。Loop Habit 的「完整备份导出失败」长期未解决（[#1854](https://github.com/iSoron/uhabits/issues/1854)），说明导出/恢复链路必须当作核心功能来测试，而不是设置页里的附属品。

## 3. 分项目分析

### 3.1 Memos：把「一句话记录」做到极致

**基本信息**：64.5k Star / 4.9k Fork / MIT / 2021 年创建 / 最近提交 2026-11-17 / 约 61 个未关闭 Issue。

**产品形态**：自托管的 Web 应用。Docker 一条命令启动，浏览器访问，Android 上用移动端网页记录。没有官方原生 App，但有 Web Clipper、Telegram Bot、API 和 MCP Server 等外围集成。

**功能面**：

- 单条 memo 可以是一句话，也可以是 Markdown 长文；
- 所有 memo 按创建日期组成个人时间线，标签跨天聚合；
- 可见性分级：`PRIVATE / PROTECTED / PUBLIC / SPACE`；
- 支持附件、评论、表情回应、置顶、分享；
- 新版引入 Space（多人共享空间）、SSO、AI 服务接口。

**核心文件与架构**：

| 文件 | 说明 |
|------|------|
| `go.mod` | Go 1.27；ConnectRPC、SQLite/MySQL/PostgreSQL 驱动、S3、goldmark、MCP SDK |
| `cmd/memos/main.go` | Cobra + Viper 启动入口，`--driver`、`--data`、`--port` 等参数 |
| `proto/store/memo.proto` | memo 的 payload 结构：tags、location、由正文计算出的属性（有无链接/任务/代码/图片、H1 标题） |
| `store/migration/sqlite/LATEST.sql` | 全量 schema，可直接作为建模参考 |
| `store/db/{sqlite,mysql,postgres}/` | 同一套 Store 接口的三种数据库实现 |
| `web/src/components` | 287 个前端组件，编辑器、时间线、标签导航等 |
| `server/api/test` | 43 个 API 层测试文件 |

**数据模型（SQLite，节选）**：

```sql
CREATE TABLE memo (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  uid TEXT NOT NULL UNIQUE,
  creator_id INTEGER NOT NULL,
  created_ts BIGINT NOT NULL DEFAULT (strftime('%s','now')),
  updated_ts BIGINT NOT NULL DEFAULT (strftime('%s','now')),
  row_status TEXT NOT NULL CHECK (row_status IN ('NORMAL','ARCHIVED')) DEFAULT 'NORMAL',
  content TEXT NOT NULL DEFAULT '',
  visibility TEXT NOT NULL CHECK (visibility IN ('PUBLIC','PROTECTED','PRIVATE','SPACE')) DEFAULT 'PRIVATE',
  pinned INTEGER NOT NULL CHECK (pinned IN (0,1)) DEFAULT 0,
  payload TEXT NOT NULL DEFAULT '{}',   -- 标签、位置、派生属性，JSON
  space_id INTEGER DEFAULT NULL
);
```

配套表：`memo_relation`（引用关系）、`attachment`、`memo_share`、`reaction`、`memo_comment`、`user_setting`（键值对配置）。

**Issues 观察**：

- 编辑器是 bug 集中区：[#6480](https://github.com/usememos/memos/issues/6480) 记录了一批 WYSIWYG 编辑器问题（Markdown 表格在富文本模式下被改写、字体样式异常），11 条讨论仍在处理中。
- 需求集中在「更细的组织方式」：日历页年月跳转（[#6535](https://github.com/usememos/memos/issues/6535)）、RSS/Atom 输出（[#6390](https://github.com/usememos/memos/issues/6390)）、附件 HEIC 自动转 JPEG（[#6520](https://github.com/usememos/memos/issues/6520)）。
- 隐私相关需求：按标签自动模糊附件（[#6127](https://github.com/usememos/memos/issues/6127)）。

**可借鉴**：

- 「输入框就在时间线顶部」的零层级记录体验，是日常记录产品最值得抄的交互骨架；
- 用 `payload JSON` 承载可变属性，schema 稳定、扩展成本低；
- 标签从正文里解析（`#tag`），同时落库成结构化字段，兼顾输入速度与检索；
- 单文件夹数据 + 单二进制部署，备份心智极低。

**应避免**：

- 自托管对普通用户门槛过高，不适合作为唯一形态；
- 富文本编辑器 + Markdown 双模式会持续产生边界 bug，首版应二选一。

> 许可证：MIT。是五个样本中对商业闭源最友好的参考实现，但仍需注意「参考设计」与「复制代码」的边界。

### 3.2 侠客日记：一套 UI 跑五个平台

**基本信息**：1.6k Star / 155 Fork / AGPL-3.0 / 2022 年创建 / 最近提交 2026-10-17 / 约 65 个未关闭 Issue。

**产品形态**：.NET 10 + Blazor。同一套 Razor 组件同时产出 Android/Windows/macOS（MAUI Blazor Hybrid）、Linux（GTK）、Web（Blazor Server / WebAssembly）。Android 要求 8.0（API 26）以上。

**功能面**：

- 本地 SQLite 存储，无需联网；
- Markdown 即时渲染，支持数学公式、脑图、图表、流程图、五线谱；
- 图片/音频/视频附件；
- 天气、心情、位置；
- 标签分类、隐私模式（应用锁）、深色模式；
- 多语言（十余种）；
- 导出多种格式、WebDAV 备份、局域网同步传输；
- 多尺寸响应式布局。

**核心文件与架构**：

| 文件 / 目录 | 说明 |
|-------------|------|
| `directory-structure.md` | 官方项目结构说明，可读性很好 |
| `src/SwashbucklerDiary.Rcl/` | 共享 Razor 组件库：Pages 106 个、Components 180 个、Services 51 个 |
| `src/SwashbucklerDiary.Maui/` | Android/iOS/macOS/Windows 壳，`Platforms/Android/AndroidManifest.xml` |
| `src/SwashbucklerDiary.Rcl.Web` / `.Hybird` | 浏览器端 / 客户端专用实现 |
| `src/SwashbucklerDiary.Server` / `.WebAssembly` | 两种 Web 托管模式 |
| `src/SwashbucklerDiary.Shared/` | 数据模型、枚举、常量 |
| `Repository/DiaryRepository/DiaryRepository.cs` | SqlSugar 仓储，`InsertNav` / `DeleteNav` 级联标签与资源 |
| `Services/Data/DiaryService/DiaryService.cs` | 业务服务层 |

**数据模型**：`DiaryModel` 通过导航属性关联 `Tags` 与 `Resources`，中间表为 `DiaryTagModel`。删除日记时对多对多关系做级联清理。仓储接口与实现分离（`IDiaryRepository` / `DiaryRepository`），服务层再包一层（`DiaryService` / `BaseDataService`）。

**Issues 观察**：

- **性能**：[#44](https://github.com/Yu-Core/SwashbucklerDiary/issues/44)（2024 年提出，至今未关）用户原话：「想要临时记录一些东西结果四五秒都打不开……不需要数学公式、脑图一大堆功能」。这是功能堆叠导致核心路径变慢的典型案例。
- **稳定性**：[#131](https://github.com/Yu-Core/SwashbucklerDiary/issues/131) 安卓频繁闪退，堆栈落在 `libcoreclr.so`（.NET 运行时），属于跨平台运行时的原生崩溃，排查成本高。
- **同步诉求**：用户多次要求 WebDAV 双向同步而不是仅备份（[#45](https://github.com/Yu-Core/SwashbucklerDiary/issues/45)、[#109](https://github.com/Yu-Core/SwashbucklerDiary/issues/109)）。
- **安全诉求**：日记内容加密（[#73](https://github.com/Yu-Core/SwashbucklerDiary/issues/73)）、导出数据库的安全问题（[#120](https://github.com/Yu-Core/SwashbucklerDiary/issues/120)）。
- **跨平台维护成本**：iOS 实际未验证、Linux 启动报错（[#114](https://github.com/Yu-Core/SwashbucklerDiary/issues/114)）。

**可借鉴**：

- 「共享 UI 层 + 各平台薄壳」的目录划分非常清晰，若确定做跨平台，这是可复用的分层思路；
- 本地优先 + WebDAV 备份 + 局域网直传，覆盖了「不想注册账号」的用户；
- 隐私模式、导出多格式，是日记类产品的必备项。

**应避免**：

- Blazor Hybrid 的冷启动与包体积代价明显，对「随手记」场景不友好；
- 首版塞入公式/脑图/五线谱等低频功能，直接拖慢主路径；
- **仓库内没有任何测试文件**（已核对完整文件树），65 个未关闭 Issue、跨五个平台，回归只能靠人工，风险很高。

> 许可证：AGPL-3.0。若产品未来闭源或做 SaaS，不能直接复用其代码。

### 3.3 June：原生 Android 日记的现代样板

**基本信息**：337 Star / 15 Fork / GPL-3.0 / 2025-12 创建 / 最近提交 2026-11-16 / 仅 16 个未关闭 Issue。

**产品形态**：原生 Android，Kotlin + Jetpack Compose + Material 3 Expressive。定位是 Google「Pixel Journal」的开源替代品。

**功能面**：

- 多媒体胶囊：照片、视频、精确位置、EXIF 查看、压缩；
- 语音备忘 + 实时波形；
- 标签分三组：Spaces、People（`@`）、Topics（`#`）；
- 音乐：流媒体链接、本地音频、波形裁剪；
- 可变字体与每篇日记独立主题、从照片取色；
- 月份日历 + 连续记录天数（streak）；
- Markdown 导入导出、心情 emoji；
- 本地优先，可选 WebDAV / Google Drive 端到端同步；
- 私密保险箱：生物识别 / PIN / 密码 / 图案；
- 自动备份，支持从 Day One、Diarium、Daily You、StoryPad 一键导入。

**核心文件与架构**：

| 文件 | 说明 |
|------|------|
| `app/build.gradle.kts` | 应用模块；`foss` / `play` 两个产品风味 |
| `core/build.gradle.kts` | 业务核心模块 |
| `core/.../database/journal/JournalEntity.kt` | 日记实体，含同步与软删除字段 |
| `core/.../database/journal/JournalDatabase.kt` | Room 数据库，version 7，`exportSchema = true` |
| `core/.../database/journal/JournalDao.kt` | 以 `Flow` 暴露查询，过滤 `deletedAt` 与 `isLocked` |
| `core/schemas/.../JournalDatabase/*.json` | 每个版本的 schema 快照，共 6 份 |
| `core/.../repository/JournalRepositoryImpl.kt` | 仓储实现 |
| `core/src/test/` | 约 44 个测试文件，含 DAO/Repository 的 fake |

**数据模型**（`JournalEntity`，节选）：

```kotlin
@Entity(tableName = "journals")
data class JournalEntity(
    @PrimaryKey val id: String,
    val title: String,
    val content: String,
    val emoji: String? = null,
    val images: List<String> = emptyList(),
    val location: JournalLocation? = null,
    val songDetails: SongDetails? = null,
    val audios: List<JournalAudio> = emptyList(),
    val tags: List<String> = emptyList(),
    val createdAt: Long = 0,
    val updatedAt: Long? = null,
    val dateTime: Long,
    val isBookmarked: Boolean = false,
    val isArchived: Boolean = false,
    val isDraft: Boolean = true,
    val isLocked: Boolean = false,
    val theme: JournalTheme? = null,
    val deletedAt: Long? = null,   // 软删除
    val syncedAt: Long? = null,    // 同步水位
    val cloudId: String? = null,   // 云端 ID
)
```

配套实体：`TagEntity`、`JournalTagCrossRef`（多对多）、`DeletedJournalTombstone`（删除墓碑，同步必需）、`SongLibraryEntity`。另有 `JournalMetadataEntity` 只查询元数据字段，避免时间线列表把正文全部读进内存——这是一个值得直接借鉴的性能细节。

**Issues 观察**：

- 需求集中在附件类型（PDF 等）、音乐裁剪时长（30 秒上限）、编辑器行为一致性（[#113](https://github.com/DenserMeerkat/June/issues/113)、[#52](https://github.com/DenserMeerkat/June/issues/52)）；
- 有明确的桌面端诉求（Windows，[#61](https://github.com/DenserMeerkat/June/issues/61)）；
- 列表密度、帮助中心、更新日志等「体验打磨」类 Issue 较多，说明核心记录链路已基本稳定。

**可借鉴**：

- **最贴近「Android 为主」的产品参考**：单模块 core + app、Compose、Room、Koin；
- 同步字段 + 软删除 + 墓碑表，是本地优先产品做同步的最小完整集合；
- 列表查询只取元数据，详情页再取正文；
- 首版就规划「从竞品导入」，降低用户迁移成本（这也是它能快速起量的原因之一）；
- 开源版与商店版用产品风味拆分（`foss` / `play`），把 Google Drive 等专有能力隔离。

**应避免**：

- 项目仅一年、迭代很快，功能面广但稳定性仍在爬坡，不要把它的全部功能当成 MVP；
- GPL-3.0，代码不能直接用于闭源产品。

### 3.4 Easy Diary：一份现成的功能需求池

**基本信息**：564 Star / 133 Fork / GPL-3.0 / 2017 年创建 / 最近提交 2026-11-16 / 约 73 个未关闭 Issue。

**产品形态**：原生 Android，Kotlin + Room + MVVM + XML 视图。分 `gms`（含 Google Drive 备份、天气）与 `foss`（F-Droid，无 Google 依赖）两个渠道。

**功能面**：

- 键盘或语音输入写日记；
- 关键词搜索并高亮；
- 日历视图、时间线视图、写作习惯柱状图；
- 日记明信片（可分享）；
- PIN / 指纹锁；
- 171 套配色主题 + 自定义字体；
- Markdown；
- Google Drive 备份与恢复；
- 位置信息、照片、心情符号（彩蛋式自定义符号）。

**核心文件与架构**：

| 文件 | 说明 |
|------|------|
| `app/src/main/java/.../data/local/AppDatabase.kt` | Room 数据库，version 7，导出 schema |
| `app/src/main/java/.../data/local/dao/DiaryDao.kt` | 复杂搜索 SQL（大小写敏感开关、时间范围、符号筛选） |
| `app/src/main/java/.../data/repository/DiaryRepositoryImpl.kt` | 仓储实现 |
| `app/src/main/java/.../presentation/*/` | 按页面拆分 ViewModel（日历、时间线、阅读、设置、锁屏等） |
| `app/schemas/.../AppDatabase/*.json` | 7 个版本 schema |
| `app/src/{gms,foss}/` | 渠道差异化代码与 Manifest |

**Issues 观察**（信息量最大的样本）：

- **数据丢失事故**：[#256](https://github.com/hanjoongcho/aaf-easydiary/issues/256) 用户升级到 `1.4.353` 后一年日记全部消失。版本 `1.4.352` 刚把数据库从 Realm 迁移到 Room。用户不敢卸载、不敢清缓存，只能求助。维护者标记了 `fixed` 但仍在等 F-Droid 发版。**这是本次调研最重要的风险案例**。
- **构建/分发**：[#212](https://github.com/hanjoongcho/aaf-easydiary/issues/212) F-Droid 无法构建，从 2023 年挂到 2026 年，17 条讨论。说明多渠道打包和可复现构建是长期负担。
- **备份与自动化**：自动保存（[#83](https://github.com/hanjoongcho/aaf-easydiary/issues/83)）、定时备份（[#157](https://github.com/hanjoongcho/aaf-easydiary/issues/157)）、Nextcloud 备份（[#94](https://github.com/hanjoongcho/aaf-easydiary/issues/94)）、CSV 导出（[#174](https://github.com/hanjoongcho/aaf-easydiary/issues/174)）。
- **产品方向**：用户明确希望它变成「2/5 分钟日记」（[#86](https://github.com/hanjoongcho/aaf-easydiary/issues/86)），以及「查看去年今日」（[#182](https://github.com/hanjoongcho/aaf-easydiary/issues/182)）。
- **输入法兼容**：微软 SwiftKey / Google 键盘相关问题（[#242](https://github.com/hanjoongcho/aaf-easydiary/issues/242)）。

**可借鉴**：

- 功能清单几乎可以直接当需求池：日历、时间线、图表、搜索高亮、明信片、主题、字体、语音输入、去年今日；
- 三种回顾视角（日历 / 时间线 / 统计图表）覆盖了不同使用习惯；
- `gms` / `foss` 渠道拆分，兼顾商店用户与开源用户。

**应避免**：

- **数据库迁移没有回滚与校验**，直接导致数据事故。迁移必须：先备份、可回滚、迁移后校验条数、并在老版本真实数据上测试；
- 备份只依赖单一云（Google Drive），FOSS 用户等于没有备份；
- 测试极薄（`app/src/test` 3 个、`androidTest` 3 个），却有 7 个数据库版本、两个渠道，风险与复杂度不匹配。

### 3.5 Loop Habit Tracker：克制与工程质量

**基本信息**：10.4k Star / 1.3k Fork / GPL-3.0 / 2014 年创建 / 最近提交 2026-10-22 / 仅 19 个未关闭 Issue。

**产品形态**：原生 Android 打卡应用。核心逻辑抽成 Kotlin Multiplatform 模块（JVM / JS / Android 共用），UI 仍然是原生 Android。

**功能面**：

- 极简打卡界面，适合老设备，速度快；
- 习惯强度评分算法（漏几天不会「断链归零」）；
- 灵活频率：每天、每周 3 次、隔天等；
- 每个习惯独立提醒，可直接在通知上打卡；
- 桌面小组件；
- CSV / SQLite 导出，支持 Tasker 等外部写入；
- 完全离线、无账号、无广告、无内购。

**核心文件与架构**：

| 文件 | 说明 |
|------|------|
| `uhabits-core/` | 纯逻辑模块（`commonMain`），不依赖 Android |
| `uhabits-core/.../database/HabitRepository.kt` | 手写 SQL 仓储，字段显式列出 |
| `uhabits-core/assets/main/migrations/09.sql ~ 26.sql` | 18 个增量迁移脚本 |
| `uhabits-core/assets/test/databases/*.db` | 真实老版本数据库样本，用于迁移测试 |
| `uhabits-core/src/commonTest/` | 56 个测试文件 |
| `uhabits-android/src/androidTest/` | 111 个测试文件 |
| `uhabits-core/build.gradle.kts` | KMP 配置：JVM + JS(IR) + Android，测试跑 Chrome Headless |

**数据模型**：`Habits` 表显式字段包括 `freq_num/freq_den`（频率分数）、`reminder_hour/min/days`、`position`、`archived`、`type`、`target_value`、`uuid`、`category`。迁移 26 号脚本只有一行：

```sql
alter table habits add column category text not null default '';
```

小步、可读、可测试的迁移风格。

**Issues 观察**：

- 导出/导入可靠性：[#1854](https://github.com/iSoron/uhabits/issues/1854) 换机时完整备份「无法复制」；[#1680](https://github.com/iSoron/uhabits/issues/1680) 重新导入 `.db` 崩溃；[#2013](https://github.com/iSoron/uhabits/issues/2013) 导入按钮失效（疑似权限）。
- 提醒与通知：[#1573](https://github.com/iSoron/uhabits/issues/1573) 已打卡仍弹通知；[#2417](https://github.com/iSoron/uhabits/issues/2417) 关闭提醒后通知仍残留。
- 小组件：[#2167](https://github.com/iSoron/uhabits/issues/2167)、[#2192](https://github.com/iSoron/uhabits/issues/2192) 尺寸与显示异常。
- 需求：自动备份与自定义目录（[#2419](https://github.com/iSoron/uhabits/issues/2419)）。
- 还停留在「首次构建 Gradle 同步失败」（[#1997](https://github.com/iSoron/uhabits/issues/1997)），说明 Android 工程门槛依旧真实存在。

**可借鉴**：

- **核心逻辑与平台解耦 + 高覆盖测试**，是五个项目里工程质量最好的；
- 迁移脚本 + 老版本数据库样本 + 迁移测试，这套做法应直接照搬；
- 极简、离线、无账号，反而形成强口碑（10k+ Star，19 个 Issue）；
- CSV 导出让用户「带走数据」，是低成本高信任的功能。

**应避免**：

- 记录粒度是「打卡」而非「内容」，无法直接套用到日记/随手记；
- 小组件与提醒是 Android 上最容易出长尾 bug 的部分，排期要留足。

## 4. 横向对比

### 4.1 数据模型

| 维度 | Memos | 侠客日记 | June | Easy Diary | Loop |
|------|-------|----------|------|------------|------|
| 主键 | 自增 id + uid | Guid | String UUID | 自增 Long | 自增 Long + uuid |
| 正文 | Markdown 文本 | Markdown + 渲染 | 富文本/Markdown | 文本 + Markdown | 无正文 |
| 标签 | 正文解析 + payload | 多对多中间表 | 多对多 + 分组 | 符号/分类字段 | category |
| 附件 | attachment 表 | Resources 导航属性 | 路径列表 + 音频/歌曲 | photo_uri 表 | 无 |
| 时间 | created/updated | 创建/更新时间 | createdAt/dateTime/updatedAt | currentTimeMillis | 时间戳 |
| 软删除 | row_status | 有删除标记 | deletedAt + tombstone | 无 | archived |
| 同步字段 | 无（服务端即真相） | 无 | syncedAt + cloudId | 无 | 无 |
| 扩展字段 | payload JSON | 强类型列 | 强类型列 + 主题 JSON | 强类型列 | 强类型列 |

**结论**：首版建议「强类型核心字段 + 一个 JSON 扩展列」。核心字段保证查询与迁移可控，扩展列承接心情、天气、主题等易变属性，避免频繁改表。

### 4.2 同步与备份

| 项目 | 账号 | 云端 | 离线 | 备份方式 |
|------|------|------|------|----------|
| Memos | 自建账号 | 自己的服务器 | 弱（依赖服务端） | 备份数据目录 |
| 侠客日记 | 无 | 无 | 强 | WebDAV 备份、局域网传输、多格式导出 |
| June | 可选 | WebDAV / Google Drive | 强 | 自动本地备份 + 端到端同步 |
| Easy Diary | 可选 Google | Google Drive | 强 | Drive 备份（仅 GMS） |
| Loop | 无 | 无 | 强 | CSV / SQLite 导出 |

**结论**：

- 「同步」和「备份」必须分开设计。同步解决多设备一致，备份解决误删/换机/跑路。
- 首版最划算的组合是：**本地数据库 + 手动/自动导出压缩包 + 可选 WebDAV**。WebDAV 覆盖面广（坚果云、Nextcloud、群晖），实现成本远低于自建云。
- 若做同步，最低成本方案是「软删除 + 更新时间戳 + 最后写入胜出（LWW）」，并用墓碑表传播删除；冲突严重时再考虑字段级合并。

### 4.3 隐私与安全

| 项目 | 应用锁 | 内容加密 | 私密分区 | 备注 |
|------|--------|----------|----------|------|
| Memos | 账号体系 | 依赖部署 | 可见性分级 | 服务端可读 |
| 侠客日记 | 隐私模式 | 用户有诉求，未见实现 | 有 | Issue #73 要求加密 |
| June | 生物识别/PIN/图案 | 保险箱隔离 | 有 | 端到端同步 |
| Easy Diary | PIN / 指纹 | 无 | 无 | — |
| Loop | 无 | 无 | 无 | 数据敏感度低 |

**结论**：日记类产品的隐私是核心卖点，但「应用锁」和「数据库加密」是两件事。建议首版做应用锁 + 私密条目隔离；数据库加密（SQLCipher）可作为后续选项，注意它对备份与迁移的影响。

### 4.4 工程化与测试

| 项目 | 测试规模 | Schema 导出 | 迁移策略 | 多渠道 |
|------|----------|-------------|----------|--------|
| Memos | Go 单测 + 43 个 API 测试文件 | SQL 全量脚本 + 版本目录 | 按年月目录增量迁移 | Docker / 二进制 |
| 侠客日记 | **0** | SqlSugar CodeFirst | 未见迁移测试 | 5 个平台 |
| June | 约 44 个 | Room `exportSchema = true` | 版本化 + schema 快照 | foss / play |
| Easy Diary | 约 6 个 | Room 导出 schema | Realm→Room 大迁移，出事故 | gms / foss |
| Loop | 56 + 111 个 | 手写 SQL | 18 个增量脚本 + 老库样本 | 无 |

**结论**：测试投入与线上事故率明显负相关。尤其要补三类测试：

1. 数据层单测（DAO / Repository / 日期与统计逻辑）；
2. 迁移测试（用真实老版本数据库文件跑升级）；
3. 导出→导入 round-trip 测试（备份功能的唯一有效验证）。

## 5. 对我们产品的建议

### 5.1 形态选择

| 方案 | 适合场景 | 优点 | 代价 | 参考 |
|------|----------|------|------|------|
| A. 原生 Android（Kotlin + Compose） | 安卓为主，需要小组件、通知、相机、后台录音 | 体验最好、系统能力完整、本地数据可靠 | 只有安卓；需要 Android 工程能力 | June / Loop |
| B. PWA / 移动 Web | 想快速验证、多人协作、以后上 Web | 迭代快、跨端、发布成本低 | 小组件/通知/后台能力受限；浏览器存储有被清理风险 | Memos |
| C. 跨平台框架 | 明确要 Android + iOS + 桌面 | 一套代码多端 | 冷启动、包体积、原生崩溃排查难 | 侠客日记 |
| D. PWA + Android 壳（TWA/Capacitor） | 想先 Web 后上架 | 兼顾速度与安装体验 | 系统能力仍受限，壳与 Web 两端都要维护 | — |

**暂定建议**：

- 如果「日常记录」的核心是**随手写 + 回顾**，且你更熟 Web：先做 **B（PWA）**，数据存本地（IndexedDB）+ 导出文件，验证留存后再考虑壳。
- 如果核心包含**提醒、打卡、桌面小组件、拍照即记**：直接做 **A（Kotlin + Compose + Room）**，这是五个样本中被验证最充分、长期维护成本最低的路线。
- **不建议首版选 C**：侠客日记的冷启动、闪退、五端维护已经证明，跨平台省下的开发量会以性能和排障成本还回去。

### 5.2 MVP 功能切分

**P0（首版必须有）**：

- 快速记录：打开即写，自动保存草稿；
- 时间线 + 日历两种回顾视图；
- 标签（从正文 `#` 解析 + 可管理）；
- 图片附件（压缩后存储）；
- 本地搜索；
- 应用锁（PIN / 生物识别）；
- 导出/导入（JSON + Markdown + 附件压缩包）；
- 自动备份到用户选择的目录（SAF）。

**P1（第二版）**：

- 心情 / 天气 / 位置；
- 连续记录天数与统计图表；
- 「去年今日」回顾；
- WebDAV 备份/同步；
- 桌面小组件、每日提醒。

**P2（谨慎）**：

- 语音、视频、音乐；
- 富文本/双链/公式；
- 多人共享空间；
- AI 摘要与回顾。

> 依据：侠客日记 #44 的差评、Easy Diary #86 的「2/5 分钟日记」诉求、Memos 的极简输入，都指向同一件事——**首版把「打开-写-保存-找到」做快，比功能多更重要**。

### 5.3 建议的数据模型（草案）

```sql
-- 记录主体
CREATE TABLE entry (
  id            TEXT PRIMARY KEY,          -- UUID
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  occurred_at   INTEGER NOT NULL,          -- 记录归属时间（可回填）
  content       TEXT NOT NULL DEFAULT '',  -- Markdown
  mood          TEXT,
  weather       TEXT,
  location      TEXT,                      -- JSON: 名称/经纬度
  is_pinned     INTEGER NOT NULL DEFAULT 0,
  is_private    INTEGER NOT NULL DEFAULT 0,
  deleted_at    INTEGER,                   -- 软删除
  synced_at     INTEGER,                   -- 同步水位
  remote_id     TEXT,
  extra         TEXT NOT NULL DEFAULT '{}' -- 扩展 JSON
);

CREATE TABLE tag (
  id    TEXT PRIMARY KEY,
  name  TEXT NOT NULL UNIQUE,
  color TEXT
);

CREATE TABLE entry_tag (
  entry_id TEXT NOT NULL,
  tag_id   TEXT NOT NULL,
  PRIMARY KEY (entry_id, tag_id)
);

CREATE TABLE attachment (
  id         TEXT PRIMARY KEY,
  entry_id   TEXT NOT NULL,
  kind       TEXT NOT NULL,      -- image / audio / video / file
  local_path TEXT NOT NULL,
  mime       TEXT,
  size       INTEGER,
  width      INTEGER,
  height     INTEGER,
  deleted_at INTEGER,
  INDEX idx_attachment_entry (entry_id)
);

CREATE INDEX idx_entry_occurred ON entry(occurred_at DESC);
CREATE INDEX idx_entry_updated  ON entry(updated_at);
```

要点：

- 时间用 UTC 毫秒整数，展示层再转本地时区；
- `occurred_at` 与 `created_at` 分离，支持补记；
- 附件只存相对路径，导出时重写为包内路径；
- 所有可同步表都带 `updated_at` / `deleted_at`，删除用墓碑而不是物理删除。

### 5.4 测试策略（与仓库规则对齐）

| 层级 | 测什么 | 工具建议 |
|------|--------|----------|
| 单元测试 | 日期归属、连续天数、标签解析、导出文件名 | JUnit / Vitest |
| 数据层 | DAO 查询、软删除过滤、分页 | Room in-memory / 内存 SQLite |
| 迁移测试 | 每个旧版本数据库样本 → 最新版，校验条数与字段 | 真实 `.db` fixture |
| 备份测试 | 导出 → 清库 → 导入，逐字段比对 | 临时目录 |
| UI 冒烟 | 新建 → 编辑 → 删除 → 搜索 | Compose UI Test / Playwright |

**硬性要求**：发版前必须跑「导出-导入 round-trip」和「迁移 fixture」两组测试，这是 Easy Diary 事故的直接防线。

### 5.5 差异化机会

1. **「2 分钟记录」定位**：首屏一个输入框，默认只存纯文本，附件与高级字段折叠；
2. **可靠的数据主权**：一键导出可读的 Markdown + 图片目录，不锁定格式；
3. **回顾优先**：时间线、日历、去年今日、随机旧日记，而不是只做「写」；
4. **无账号可用**：本地优先，云同步是可选增强，不做强制注册。

## 7. 下一步

**建议先做的事**：

1. 真机安装 June、侠客日记、Easy Diary、Loop，各记录 3 天，重点观察：首次启动耗时、输入到保存的步骤数、回顾体验、备份流程；
2. 用 30 分钟分别走一遍「导出 → 换机导入」，记录失败点；
3. 确定形态（见 5.1）后，再定技术栈与仓库结构。

**需要产品决策的三个问题**：

1. 是否需要**多设备同步**？如果只是单机，首版可以完全不碰同步，把备份做扎实。
2. 是否需要**账号/云服务**？如果需要，成本与合规模块会显著增加。
3. 记录的核心单位是「一篇日记」还是「多条碎片」？前者偏日历/回顾，后者偏时间线/标签，直接影响首页设计。

```bash
npm test            # 结构 + 相对链接，快速、可离线，提交前必跑
npm run test:links  # 额外检查 38 个外部链接，较慢，网络抖动时会跳过并告警
```
